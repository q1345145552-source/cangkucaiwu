# 第十九轮：主管不得核实本人的加班

基线fa7708a；本轮业务代码只修改 `backend/app/api/v1/overtime.py` 中的核实函数并导入修改日志服务。前端、模型、迁移、工资、考勤、打卡代码没有变化，未部署。

## 判定口径

现有 `POST /api/v1/overtime/{task_id}/verify` 是逐人核实，一个任务可以同时分配多人。本轮采用用户允许的“被核实那个人”口径，判断本次to_verify中的每条分配记录：

- `OvertimeAssignment.user_id == 当前主管账号ID`；或
- 对应员工档案 `Employee.user_id == 当前主管账号ID`；或
- 分配记录employee_id等于当前主管账号已关联的attendance_employee_id。

满足任一即HTTP403“本人不能核实自己的加班”。不比较名字，不把“任务由这个主管创建”当作整单禁批条件。即使任务由管理员创建，主管也不能自行核实其中自己的那份。

检查在实际小时、金额、争议或日志写入前进行；混合请求含自己时整批拒绝，不先核别人再部分失败。只请求核实别人时正常放行，即使同一个任务另有主管本人尚未核实的记录。

员工已经确认过的分配记录沿用原逻辑跳过，不更改它的数据，不算本次实际核实；只为实际核实的分配记录写日志。

## 角色与原有差异

- 主管有加班权限时可核实别人，不能核实自己；原有加班权限依赖保留。
- 仓库管理员可核实所有本仓授权记录。
- 检查发现基线实际把super_admin排除在核实角色名单外，与本轮“超管也能核实”的明确要求不同。本轮仅在核实接口将super_admin加入允许名单；仓库范围过滤原样保留，其他加班角色限制不改。
- 财务、劳工仍不能核实。

## 留痕

每条实际核实的OvertimeAssignment写一条DataChangeHistory：

- module=`overtime`、operation_type=`verify`、record_id=分配记录编号。
- 保存operator_id/operator_name、仓库编号、任务ID、员工ID、绑定账号ID。
- before/after保存actual_hours与earned_amount；after另含verified_by及verified_at。
- 本例主管核劳工：operator_id=4，task_id=2，record_id=2，verified_at=`2026-10-16T16:51:36.275455+07:00`。
- 本例管理员核主管：operator_id=1，task_id=1，record_id=1，verified_at=`2026-10-16T16:51:36.281266+07:00`。
- GET `/api/v1/history?module=overtime`可读回两条对应记录。
- 日志与核实同一请求事务；注入日志失败后，任务、金额、实际小时及日志均回滚。

当前修改日志前端未配置overtime/verify中文标签，会回退显示英文键；详情仍有操作者、时间及金额。本轮按要求不改前端。

## 员工功能与金额

- 主管、劳工分别确认自己已核实的加班成功；分别提交原因及照片提异议成功。
- 核实后清除争议的原逻辑保留：主管处理劳工争议成功，管理员处理主管争议成功。
- 按实际1.1小时核实，仍向上取3个半小时×25＝75元；两人合计150元。
- 实际算工资：劳工正常一天基础工资400，加班75，实发475。工资代码及公式未改。
- 完全同名但账号不同的劳工，主管仍能核实；修改主管姓名也不能绕过本人拦截。
- 单独测试assignment.user_id、Employee.user_id、attendance_employee_id三种身份路径，均不能绕过。
- 外仓任务404，混入别的任务/外仓分配记录400，原归属校验保留。
