第十二轮：全天假当天禁止打卡、净工时归零
完成验收：2026-10-20（泰国时间）
环境：本地隔离数据库、真实 HTTP 请求和最终前端构建；没有操作生产，没有部署。
接口/工资固定测试日为 2026-10-16，浏览器固定数据日为 2026-10-19。

一、第一步：已通过全天假不能打卡
POST /api/v1/clock-in，四个时点均返回 400：
{"detail":"今日已请全天假 不能打卡"}
即使此前该时点已经打过，也先执行全天假拦截，不从重复打卡返回绕过。
仅匹配本仓、本人档案、当天、已通过、全天假；历史空时长类型按原有全天假含义兼容。
劳工、纳入考勤主管、已绑定账号、历史手机号/姓名匹配均已验证。
GET /clock-in/today 新增 full_day_leave，原有返回字段保留。

二、第二步：半天假仍能打卡
已通过下午半天假，上午 session=1：200。
{"message":"早上上班打卡成功","session":1,"clocked_in_at":"2026-10-16T09:00:00","status":"normal","penalty_amount":0,"photo_path":null}
上午半天假及按小时假也不被新增规则拦截。

三、第三步：全天假与旧打卡同时存在，工时归零
实际打卡 09:00 / 12:00 / 13:00 / 18:00，原始打卡工时 clock_hours=8.0。
考勤状态仍为“请假”，净工时 work_hours=0.0。
工资当天 hours=0.0，attendance=0.0，base_pay=0.0，net_pay=0.0。
日薪、时薪、月薪均为上述结果；只有两个打卡时点的场景也归零。
原始打卡和请假记录逐字段保留，四张原有工资单逐字段不变；只在明确调用新计算时生成新单。
考勤和工资调用同一个 full_day_net_hours，出勤零沿用原有全天假出勤判断。

四、第四步：已有打卡时批准全天假，提示但不自动处理
先打卡，再批准当天全天假，实际返回 200：
{"message":"已批准","warning":"该员工当天已有打卡记录 请确认是否需要处理","clocked_dates":["2026-10-16"]}
审批人、审批时间、已通过状态照常保存。打卡记录没有删除或改写。
管理员代录直接生效的全天假也提供相同提示，并列出有打卡的日期。
管理员浏览器实际点击“通过”后触发提示弹窗；关闭提醒后审批已完成，日历显示请假。
前端仅增加对 warning 的显示，没有改变审批步骤和结果。

五、第五步：待审批、已驳回不拦
待审批全天假：上午打卡 200，status=normal。
已驳回全天假：上午打卡 200，status=normal。
外仓员工不因本仓全天假被拦。

六、第六步：三语文字和手机
中文：今日已请全天假
缅甸语：ယနေ့ တစ်နေ့လုံး ခွင့်ယူထားသည်
泰语：วันนี้ลาเต็มวันแล้ว
中文、缅甸语、泰语组件渲染测试通过。员工端现有语言入口仍是缅甸语/泰语，未增加语言选项。
浏览器分别切换缅甸语和泰语，390×844 尺寸下四个按钮均 disabled=true，灰色 rgb(156,163,175)。
截图：images/full-day-leave-mobile-my.png、images/full-day-leave-mobile-th.png。
页面已打开后再被批准的情形，后端仍会拒绝打卡，前端收到拒绝会刷新当天状态。
