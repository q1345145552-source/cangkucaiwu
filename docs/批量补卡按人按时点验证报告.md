# 批量补卡：按人按时点验证报告

日期：2026-10-18。以下均为本机隔离数据库、真实接口和浏览器测试结果，不是线上数据。本轮未部署，未给线上员工补卡。

## 功能与权限

- 新接口：`POST /api/v1/clock-in/batch-makeup`。
- 入参：`date`、`employee_ids`、`sessions`（1—4）、`reason`（必填，最多500字）。员工、时点去重后按组合处理。
- 仅 `warehouse_admin` 可调用；主管、财务、劳工、超管即使有考勤权限也返回403：`{"detail":"只能由仓库管理员批量补卡"}`。不新增可勾权限。
- 四个打卡时点调用原有 `get_session_times`，从当前仓配置中心读取。新记录保留 `is_makeup=true`、补卡账号、补卡操作时间和原因。
- 只补空缺；已有正常或迟到记录都跳过，不覆盖。按员工/账号顺序加行锁，防止两个批量请求同时补同一账号；同请求使用原会话事务提交。
- 未来日期、无原因、无员工、无时点、非法时点、跨仓、已删除、离职、未关联账号或关联外仓账号会拒绝。整批先校验再写入，不能让前半批成功、后半批因员工校验失败。
- 本轮新增批量路由；原 `makeup_clock_in` 单条补卡函数逐函数 AST 比较完全一致，主管仍能单条补卡。工资、考勤计算、请假、作息服务及权限清单均未修改。

示例：

```json
{"date":"2026-10-18","employee_ids":[1,3],"sessions":[1,2,3,4],"reason":"系统故障"}
```

## 新字段及启动迁移

表：`clock_in_records`。字段：`makeup_counts_toward_limit`，布尔、非空、默认 `true`。

`backend/scripts/seed.py` 增加独立迁移帮助函数，并在启动初始化时调用：

```sql
ALTER TABLE clock_in_records
ADD COLUMN IF NOT EXISTS makeup_counts_toward_limit BOOLEAN NOT NULL DEFAULT true;
```

单独保存点执行，失败打印字段名并抛错，防止缺列仍继续启动。老记录及普通补卡沿用默认true；系统故障批量补卡显式false。额度统计仍按自然月、按日期去重，只新增“计入额度=true”条件。

嵌入式 PostgreSQL 真实执行两组测试：旧库加列、重复启动、失败保存点回滚与重试、旧值保持、普通新记录默认true、批量false不被下一次迁移改回，全部通过。

本仓5名员工：员工1、选中员工B、请假员工A、请假员工B、休息员工。另有外仓员工用于隔离测试。

|---|---:|---|---|
| 员工1 | 4 | 1/2/3/4 | 4/4，8小时 |
| 选中员工B | 4 | 1/2/3/4 | 4/4，8小时 |

浏览器提交成功提示与数据库一致。`GET /clock-in/records` 对这8条返回 `is_makeup=true`、`makeup_by=1`、操作时间非空、原因“系统故障”，原补卡标记显示机制无需改动。

## 部分时点与重复提交

在2026-10-17，仍选2人，仅勾1（早上上班）和4（下午下班）：

```json
{"message":"批量补卡完成：建了4条，跳过0条","created_count":4,"skipped_count":0}
```

每人恰好2条，数据库各为 `session=1,4`；时点2/3没有记录，考勤显示2/4。390×844手机实际提交与接口测试一致。

重复2026-10-18的2人四时点请求：

```json
{"message":"批量补卡完成：建了0条，跳过8条","created_count":0,"skipped_count":8}
```

同请求重复员工编号/时点不会重复建；已有迟到记录的时间、状态、罚款和所有字段快照原样保留。

工资只对隔离员工手工发起计算：2026-10-18明细8小时、出勤1天，日薪400，基本工资400、实发400。原有工资单在补卡与读取考勤后全字段快照不变。

现有工资流程不结算尚未过完的今天，因此工资测试仅把工资侧测试日期推进到次日后手动计算；生产代码未改这个规则，也没有自动重算历史工资单。
