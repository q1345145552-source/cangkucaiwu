# 状态与历史兼容

本轮没有新增模型、数据库列或结构迁移，也没有运行生产迁移。复用既有 `varchar(20)` 状态、逐笔拨付表唯一 `recharge_request_id` 和事务内 `data_change_history`。原金额上限、默认值、币种与余额/成本计算函数没有修改。

## 新申请

`pending`（待核验）→ `verified`（待批准）→ `approved_ready`（待执行）→ `executed`。

核验由财务或管理员独立完成，批准只由管理员完成。两步均不出款。执行由有备用金菜单权限的独立财务完成；实际申请人或受益人是财务时，也允许独立管理员执行。申请人、账户受益人及正式员工关联均用于本人判断。主管不能核验、批准或执行。每一步事务记录操作者、仓库、动作和对象快照；执行必须匹配批准快照。修改金额、受益人等会使旧批准证据失效。

并发执行按申请、仓库、备用金、付款账户锁序串行化；唯一申请拨付关联再保护一次。已执行的重复请求返回409，不再扣公司账户、加备用金或新增支出。执行失败整笔回滚，保留原批准状态，允许独立执行人重试。

手工开销 `pending`→`verified`→`approved`，驳回仍是 `rejected`。登记及审批沿用原“拨付形成成本、后续用途记录不再形成第二笔成本”口径。核验不直接批准。管理员修改已核验但未批准的手工开销或凭证时，退回待核验，旧证据不能批准新内容。报销关联开销的批准不再写成已付款；经有效备用金批准后，独立付款人通过既有报销付款接口执行，不重复扣除转入备用金时已经预留的余额。费用审批、预支关联开销继续在原模块处理，不借备用金核验入口改变。

## 历史数据

- 历史 `approved` 且已有逐笔拨付：保留原数据，不改成新状态、不重付；再次执行拒绝。
- 历史 `approved` 但无可核验批准证据/拨付事实：不猜测已付款或应付款，不自动执行，返回409。如何核对这类历史账实不符记录属于后续人工处置范围，本轮没有代批、补数据或自动创建替代申请。
- 历史 `pending`：保留待处理；用户可以明确进行新核验、批准和执行。没有批量补批准。
- 历史已批准普通开销保留只读，不重新核验、执行或改变旧费用。历史无凭证待审开销须主动补凭证才能核验；驳回不要求先补凭证。
- 旧 `/accounts/{id}/topup` 备用金直拨接口仍注册，但对所有角色拒绝并说明新流程，不能作为兼容绕过。
- 旧客户端提交审批附带付款账户字段不会自动付款；必须调用执行接口。页面已改为分别核验、批准、执行。

## 回退说明

无结构升级/降级 SQL。不要在存在新状态记录的环境直接回退到会“批准即付款”的旧业务代码：旧客户端不识别新状态，旧批量审批也不能辨认新批准证据。需要回退时应先停止相关写入、逐笔核对新流程记录并保留拨付与审计事实，再由用户安排独立回退方案。本轮没有实施回退或修改任何真实历史数据。
