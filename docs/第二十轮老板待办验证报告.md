# 第二十轮：老板待办

验证环境：本地隔离数据库和真实前端构建，未连接或改动线上数据，未部署。

## 实现和口径

新增 GET `/api/v1/dashboard/boss-todos`：

- `advances`：`count`、`items`，每笔含编号、仓库、员工编号/姓名、金额、币种、日期。只读 pending。
- `overtime`：`count`、`items`，每条含逐人分配编号、任务编号、仓库、员工编号/姓名、日期、计划小时数、是否异议。
- 条数直接取同一次查询明细的长度，无分页截断。加班按人计条数，一项两人任务计两条。
- 需要核实、任务未完成、员工未确认，且实际工时尚为空或存在待处理异议，才进加班待办。实际工时为0也是已核实；已核实但待员工确认不计入。
- 仓库管理员、主管、财务只查账号已授权仓库，沿用业务列表的 get_wh_ids；伪造其他仓请求头不越权。超管返回两类0和空数组；劳工拒绝。

仪表盘新增待办卡片，支持手机。预支入口带 `approval_status=pending`，加班入口带 `pending_verification=true`。加班任务与逐人记录均按相同谓词过滤，过滤在分页前执行；待核实模式加载后续分页。

由于旧预支页无审批入口，为满足“点进去批一笔”，补了审批状态筛选、状态显示和仓库管理员通过/驳回按钮，直接调用第十八轮接口。没有改后端审批规则。既有预支新增/删除、加班核实/确认/异议处理函数保持一致，已有工资单不改。

目标业务页继续执行原权限：主管/财务可读取提醒并不代表获得审批或核实权，也不自动授予对应业务权限。

## 数字验证

| 场景 | 待批预支 | 待核实加班 |
|---|---:|---:|
| 隔离数据库直接查数 | 3笔 | 2条 |
| 同一数据接口返回 | 3笔 | 2条 |
| 各处理一项后接口返回 | 2笔 | 1条 |
| 全部处理后 | 0笔 | 0条 |

浏览器使用另一套同样初始数据，屏幕实际显示3笔/2条。点预支卡片后筛选已是“待审批”，通过100泰铢一笔，列表即时移除，返回仪表盘为2笔/2条。点击加班卡片，勾选“只看待核实”，现有核实弹框保存该任务两位员工各1小时，共100泰铢，返回为2笔/0条。手机完成一笔驳回及最后一笔通过后，待办0笔/0条并显示“暂无待办”。

主管、财务读取同仓提醒与管理员一致，即使未授予业务权限也可读取提醒。另仓财务只读另仓预支，超管空、劳工403、未登录拒绝。单独验证已核实、0小时、已确认、已完成、不需要核实均排除；未处理异议保留，重新核实后消失。205条明细计数无截断。

返回仪表盘会重新请求，重新聚焦及恢复可见也刷新；后端 `Cache-Control: no-store`。失败显示错误，不用0伪装没有待办。
