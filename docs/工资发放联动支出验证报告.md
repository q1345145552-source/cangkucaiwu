# 工资发放联动运营支出

本轮只做后端，未部署。以下全部是独立测试库中的真实接口/数据库结果，不是生产数据。

## 采用方案

- 每张工资单对应一笔运营支出；批量发放共用同一个账户，仍分别记账，每笔备注人数为1人。
- 工资表新增 `expense_record_id`，外键指向 `expense_records.id`，唯一索引防止一个支出被多张工资单引用。旧记录默认NULL，不追溯历史支出。
- 支出分类通过当前仓库＋名称“员工工资”＋类型expense＋分组operating查找，不写死编号。启动幂等补齐所有存量仓库，新仓库使用共同默认分类定义创建。
- 账户来自现有 `payment_accounts`。共享GET `/accounts`增加“工资”读取权限，主管只勾工资也能取账户列表；账户写权限不变。
- 单笔/批量发放必须传 `account_id`。不选、外仓、不存在、停用、非泰铢账户均拦住；工资现有币种是THB，本轮不做换汇。
- 工资标为发放与创建支出使用同一个请求数据库事务；没有中途commit。单笔、批量及撤销对工资行加锁，批量按ID固定顺序加锁；同一单不会重复记支出。
- 撤销采用用户允许的“删除关联支出”方案。工资退回confirmed＋未发放，关联清空；修改日志保留原金额、账户、工资编号及备注“因为撤销发放而冲销”。没有给全部支出引入新的冲销状态。
- 联动支出不能从支出页单独改或删，提示“工资联动支出请在工资模块撤销发放后处理”。普通支出保留原流程。

## 接口变化

- `POST /payroll/{id}/disburse`：JSON新增 `account_id`，保留 `signature_base64`。新增返回 `expense_record_id`、`account_id`，原字段保留。
- `POST /payroll/batch-disburse`：`record_ids`保留，新增 `account_id`；新增返回 `total_net`、`expenses`、`account_id`。
- `POST /payroll/{id}/revoke-disbursement`：新增返回 `reversed_expense_id`。历史未关联支出的已发放单仍可以正常撤销，不制造历史支出。
- 工资列表每条新增 `expense_record_id`；支出列表每条新增 `payroll_record_id`，普通支出为NULL。页面跳转按钮留下一轮前端实现。
- 现有GET `/accounts`按ID返回账户，下一轮界面可默认选现金或第一个。**本轮旧前端尚未发送account_id，发放会提示“请选择工资发放账户”；须与下一轮账户选择界面一起部署。**

## 6. 原子性、历史与迁移

- 注入单笔记账失败：工资、支出、修改日志全部回滚。
- 注入批量第二笔失败：第一笔与第二笔一起回滚。
- 撤销删除支出后注入日志失败：支出删除和工资撤销均回滚。
- 已发放老单ID3逐列比较不变，`expense_record_id`仍NULL，没有补支出。启动不计算工资。
- 嵌入式真实PostgreSQL执行旧表加列、索引、分类迁移，两次重复执行无重复分类；注入加列或建索引失败，独立保存点回滚，之前的迁移保留；恢复后重跑成功。
- 已有关联字段的工资记录重跑迁移后关联保留。旧工资金额和已发放状态保留，旧支出表仍空。
- 金额0允许按0入账；负数、非整分金额拒绝，避免工资与支出不一致。
