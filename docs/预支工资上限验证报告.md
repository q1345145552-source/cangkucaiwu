# 预支不能超过自己的工资

日期：2026-10-19。基线：`c78dbbf`。金额验收均使用本地隔离库，没有登记生产预支、修改历史记录或重算生产工资；本轮不部署。

## 登记时的校验口径

月工资标准来自员工当前关联的本仓薪资模板：

| 类型 | 计算方式 | 样本 |
|---|---|---:|
| 按月 | 模板月薪 | 10,000 → 10,000 |
| 按天 | 日薪 × 26 | 400 → 10,400 |
| 按小时 | 时薪 × 8 × 26 | 50 → 10,400 |

现有系统的按小时模板在 `amount` 中保存的是日薪，页面原文也是“按小时和按天填日薪”。原算薪先把模板金额除以8得到时薪。本轮沿用这个存储定义：模板填400，时薪为50，再乘8乘26，额度10,400；没有把400错当时薪放大8倍。原工资算法和薪资模板界面都未改。

占用是 **已通过且未结清的剩余金额＋待审批的全额金额**，按员工编号和仓库筛选，不限制所属月份或预支来源，也不把待审批重复算两次。已结清、已驳回不占；历史结清状态为空但仍有已通过预支余额的，不当作已结清漏掉。

可用金额为月标准减占用，最低显示0。占用加本次严格大于月标准才返回400；恰好等于标准允许。使用十进制金额比较，不先把每笔外币四舍五入再比较；可用提示向下显示到分，避免提示可用金额高于实际额度。

登记在同一个事务持有员工行锁后查额度，避免同一员工同时登记时都读到同一份可用额度。超额在新预支、联动支出和备用金开销写入之前返回，拒绝前后账目快照一致。

## 第一步、第二步：月工资10,000

以下为隔离库真实接口返回的摘录。管理员登记8,000：HTTP **200**。

```json
{
  "message": "预支记录已创建",
  "id": 1,
  "approval_status": "approved",
  "limit_check": {
    "checked": true,
    "currency": "THB",
    "monthly_salary": 10000.0,
    "occupied_amount": 0.0,
    "requested_amount": 8000.0,
    "available_amount": 10000.0,
    "remaining_amount": 2000.0
  }
}
```

同一员工再登记3,000：HTTP **400**，没有新增预支、支出或备用金开销。

```json
{"detail":"预支合计不能超过当月工资，当前可用 2000.00 元"}
```

## 第三步：待审批也占额度

| 操作 | HTTP | 审批状态 | 登记后总占用 | 剩余额度 |
|---|---:|---|---:|---:|
| 前面已登记8,000，再由主管给自己登记1,000 | 200 | 待审批 | 9,000 | 1,000 |
| 再登记1,000 | 200 | 待审批 | 10,000 | 0 |
| 再登记0.01 | 400 | 未新建 | 10,000 | 0 |

最后一笔实际返回：

```json
{"detail":"预支合计不能超过当月工资，当前可用 0.00 元"}
```

原验收文字中“8,000＋1,000后再加1,000应该拒绝”与“不超过”不一致。因此按明确的“大于才拒绝”执行：达到10,000允许，超过才拒绝。两个待审批1,000都已经占用，无法继续登记绕过额度。

另测满额待审批10,000：新增被拦；管理员驳回这笔后，再登记10,000成功，接口返回原占用0。

## 第四步：结清后恢复额度

额度场景中，将上述记录在隔离库设置为已结清后，再登记1,000：HTTP **200**，返回摘录：

```json
{
  "message": "预支记录已创建",
  "id": 4,
  "approval_status": "approved",
  "limit_check": {

    "requested_amount": 1000.0,
    "available_amount": 10000.0,
    "remaining_amount": 9000.0
  }
}
```

同时另跑真实工资结清流程：日薪400，月额度10,400；登记1,000后，再申请10,400被拦。实际算三天工资：工资基数 **1,200**、预支抵扣 **1,000**、实发 **200**，原预支结清。随后登记10,400成功，占用0、剩余0。没有新增预支作废功能或修改工资抵扣公式。

## 没有模板的提示

无薪资模板员工登记99,999仍为HTTP **200**，实际返回：

```json
{
  "message": "预支记录已创建；该员工没有薪资模板 无法校验预支上限",
  "limit_check": {
    "checked": false,
    "currency": "THB",
    "warning": "该员工没有薪资模板 无法校验预支上限"
  }
}
```

前端原来写死了成功提示，会吞掉后端的这句话。本轮仅将登记成功提示改为显示后端 `message`；原表单字段、按钮、菜单、排版都未改变。组件测试验证了这句提示能显示，以及超额错误原样显示、保留表单供修改。

## 人民币与泰铢共用额度

经确认，人民币折成泰铢后与泰铢预支一起校验。登记日期取该笔请求的 `advance_date`；已有未结清预支也分别取自己的 `advance_date`。只查询本仓、该泰国日期结束之前生效的最新汇率，支持CNY→THB和反向汇率，不取其他仓库或之后日期的汇率。不改金额原币种，不修改汇率表。

实测月标准10,000：

- 旧笔10月16日，人民币1,000，汇率5，占5,000泰铢。
- 再登记泰铢2,000，总占用7,000。
- 新笔10月18日，人民币500，汇率6，占3,000泰铢，总占用恰好10,000，允许。
- 再登记人民币1被拒，可用0；拒绝后无新预支、支出或备用金开销。
- PostgreSQL实测日期边界：10月16日16:59:59 UTC仍属泰国16日，汇率5；17:00 UTC已属17日，汇率6。16日的旧笔仍取5。

有薪资模板却缺少该笔所需的历史汇率时，返回“请先设置汇率后再登记预支”，不静默跳过。已有外币未结清预支缺汇率时，登记新的泰铢预支也会同样提示；不自动猜填历史汇率。无薪资模板仍按前述规则允许登记并提示无法校验。换汇仅用于登记额度校验，工资抵扣口径保持原样。
